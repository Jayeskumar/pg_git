# Benchmark results

Generated by `bench/report.py` from `bench/results/results.json`. PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1), pgbench scale 50 (cluster ≈ 777 MiB at v1, 852 MiB at v12), 12 versions, 4 vCPU / Linux 6.18.44; every tool used zstd level 3 and, where it supports it, 4 parallel processes. Caches were warm (a single container), so the times are comparisons between tools, not absolute figures.

## Integrity checking of the repository itself

`pgit fsck` (decode and hash every object, then check reachability) took 2.55 s; `pgit verify --all` (rebuild every file of all 12 versions in memory and compare whole-file SHA-256) took 29.70 s.

One byte was flipped in the middle of each tool's largest repository file (a copy), and the tool's own verification command was run on it:

| tool | detected | how | versions affected |
|---|:-:|---|---:|
| pgit | ✅ | pgit fsck | 12/12 |
| pg_basebackup (full) | ✅ | pg_verifybackup after extraction | – |
| pgBackRest file-incr | ✅ | pgbackrest verify (exit code 0, damage only in report) | 1/12 |
| pgBackRest block-incr | ✅ | pgbackrest verify (exit code 0, damage only in report) | 1/12 |
| restic | ✅ | restic check --read-data | – |
| git | ✅ | git fsck --full | – |

*Versions affected* counts the snapshots the tool reported as damaged. It depends on *which* file was hit, so it is not a like-for-like comparison. For pgBackRest the largest file happened to belong to the newest incremental. For pgit it was the first pack, which holds pages that every later snapshot shares (dedup) or builds deltas on. That is the inherent trade-off of deduplicated and incremental storage: a damaged pgBackRest *full* backup also invalidates the incrementals that depend on it. pgit detects such damage on every read and names the affected objects, but it cannot repair from a single copy, so keep the repository on redundant storage.
